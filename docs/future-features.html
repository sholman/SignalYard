MCP Authentication → OAuth Proposed

Goal: Per-user OAuth on the /mcp endpoint for Claude connector integration Drafted: 2026-08-10 Status: Design / not started

This document captures what it would take to move SignalYard's MCP endpoint from a single shared API key to per-user OAuth, so it can be added as a remote connector in Claude (claude.ai custom connectors and Claude Code) and each user authenticates as themselves. It is a design note for future work — nothing here is implemented yet.

1. What we have today

The /mcp endpoint is guarded by a single global secret (Mcp:ApiKey) sent as an X-Api-Key or Authorization: Bearer header, validated in constant time by McpApiKeyAuthenticationHandler. A successful request always produces the same fixed identity — McpInvestigator — with read access to every application's logs. The endpoint fails closed: no configured key means every request is rejected.

There is no user model behind the MCP endpoint. The tools in LogInvestigationTools are static and receive no caller context, so there is nothing to scope access by. Relevant code today:

  • src/SignalYard.Web/Auth/McpApiKeyAuthenticationHandler.cs — the shared-secret handler
  • src/SignalYard.Web/Program.cs (lines ~62–117) — scheme registration and the /mcp authorization policy
  • src/SignalYard.Web/Mcp/LogInvestigationTools.cs — the three read-only tools

2. The shift OAuth requires

/mcp becomes an OAuth 2.0 Resource Server. Instead of checking a shared secret, it validates a per-user bearer JWT issued by an Authorization Server (AS). Each user runs a browser login flow that Claude drives, and Claude attaches their token to every MCP call. The .NET SDK already in the project (ModelContextProtocol.AspNetCore 1.4.0) provides the server-side plumbing for this (protected-resource metadata + the WWW-Authenticate challenge).

3. The one hard constraint that drives the whole design

⚠ Critical constraint

Claude's connector system requires Dynamic Client Registration (DCR). Claude registers itself at runtime via a /register endpoint and does not let the user paste a client ID / secret. The AS must publish /.well-known/oauth-authorization-server including a registration_endpoint, advertise S256 PKCE ("code_challenge_methods_supported": ["S256"]), and rotate refresh tokens for public clients.

Entra ID — what SignalYard already uses for the UI — does not support open DCR. So we cannot simply point Claude at the existing Entra tenant. Choosing where DCR-capable tokens come from is the real decision; the SignalYard code changes are small by comparison.

4. Work breakdown

  1. Stand up an Authorization Server that supports DCR the real work

    Three routes, in order of best fit for a self-hosted OSS tool:

    RouteWhat it isCost / trade-off
    Self-host OpenIddict Free, MIT-licensed, ASP.NET Core-native AS. Supports DCR + PKCE. Runs inside or beside SignalYard. Federate the actual login to the existing Entra so users sign in with the same account. Most code; you own a token-issuing security surface.
    Managed MCP-auth provider WorkOS AuthKit, Stytch, Scalekit, Auth0 — several now market MCP auth with DCR + metadata + token issuance out of the box, and can federate to Entra. Least code; external dependency, likely paid.
    DCR shim / proxy in front of Entra Implement /register + metadata ourselves, map registrations onto one pre-registered Entra app, and proxy the token exchange. Fiddly; effectively re-implementing part of an AS anyway.

  2. Wire SignalYard as a resource server small, well-supported

    • Add AddJwtBearer pointing at the AS; validate issuer, audience / resource (RFC 8707 — the token must be minted for SignalYard, not another resource), and scopes.
    • Add the SDK's MCP auth handler (McpAuthenticationHandler / .AddMcp(...)) so a tokenless request returns 401 + WWW-Authenticate pointing at /.well-known/oauth-protected-resource. That discovery chain is exactly what Claude follows.
    • Swap the /mcp policy in Program.cs (~lines 113–117) from the McpApiKey scheme to the JWT/MCP scheme.
    • Decide the fate of McpApiKeyAuthenticationHandler: keep it as a second scheme for headless / CI use (dual auth), or retire it. The existing GET /mcp → 405 short-circuit and stateless transport stay as-is.

  3. Add a per-user identity / authorization model only if "their own auth" should mean "their own access"

    • Today there is no user↔application access model — any authenticated caller reads all apps. OAuth alone gives a real user principal (better audit + per-user revocation / expiry) but still global read unless we add scoping.
    • To scope it: introduce a user→app access entity (a new Table Storage table — none exists today), thread the ClaimsPrincipal into the tools (currently static with no caller context — inject IHttpContextAccessor or pass identity through), and filter list_applications / query_logs / get_log_stats accordingly.

5. Recommendation

✔ Suggested approach

The SignalYard-side changes are roughly a half-day; the decision that actually matters is where DCR-capable tokens come from. For a self-hosted, open-source tool, default to OpenIddict federated to Entra — no commercial dependency, and users sign in with the Entra account they already have.

Treat per-user authorization scoping (step 3) as a separate follow-up. Ship per-user authentication first (real identities, revocation, audit) while keeping global read, then add access scoping later.

6. Smaller gotchas

  • HTTPS + public reachability for the AS metadata and /register endpoints.
  • DCR isn't optional. claude.ai custom connectors strictly need DCR; Claude Code can do OAuth too, but relying only on Claude Code doesn't remove the requirement.
  • Login federation matters. Whichever AS route we pick, wire its user authentication to the existing Entra so we don't create a second identity silo.
  • Token audience binding (RFC 8707) must be validated — reject tokens minted for a different resource.

7. Next steps & open questions

  • Confirm the AS route (OpenIddict self-host vs managed provider).
  • Prototype the resource-server wiring against a throwaway AS to validate the Claude discovery + DCR flow end-to-end before committing to the AS choice.
  • Decide whether to keep the global API key as a fallback scheme for CI / headless use.
  • Decide whether per-user authorization (app-level access scoping) is in scope now or a later phase.
  • Verify exact SDK API names/signatures against the installed ModelContextProtocol.AspNetCore version when implementation starts.
